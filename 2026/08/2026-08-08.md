## 1. VM起動時のネットワーク待機を改善

検証環境では、次の2つのネットワークインターフェースを使用している。

* `eth0`

  * Hyper-VのDefault Switch用
  * Ubuntuの更新やパッケージ取得時のみ使用
  * 完全隔離中はHyper-V側で切断する

* `eth1`

  * LAB-PRIVATE用
  * VM間通信に使用
  * lab-target01：`10.77.0.10/24`
  * lab-client01：`10.77.0.20/24`

Default Switchを切断した状態でVMを起動すると、Ubuntuがネットワーク接続の完了を待ち続け、タイムアウトするまで約2分かかっていた。

また、2台のVMをほぼ同時に起動することが多いため、LAB-PRIVATE側の`eth1`についても起動時の待機が発生する場合があった。

そこでNetplanの設定で、ネットワークインターフェースを起動時の必須条件から外した。

例：

```yaml
eth0:
  dhcp4: true
  optional: true
```

固定IPを設定している`eth1`にも同様に、

```yaml
eth1:
  addresses:
    - 10.77.0.10/24
  optional: true
```

のように`optional: true`を追加した。

`optional: true`は、そのNICを無効にする設定ではなく、

「そのNICの通信準備が完了していなくても、OSの起動を待たない」

という指定である。

設定後はVM起動時の長いネットワーク待機が解消された。

## 2. Nginxの正常状態を確認

前回作成した正常状態からVMを起動し、Nginxが正常に稼働していることを確認した。

```bash
sudo systemctl status nginx --no-pager
```

また、lab-client01からlab-target01へHTTP通信を行い、

```bash
curl -I http://10.77.0.10
```

`HTTP/1.1 200 OK`が返ることを確認した。

## 3. Nginx設定ファイルの文法チェック

Nginxには、設定ファイルを反映する前に文法を検査する機能がある。

```bash
sudo nginx -t
```

正常状態では、

```text
syntax is ok
test is successful
```

と表示された。

このコマンドを利用すれば、設定変更後にNginxを再起動する前に、文法ミスがないか確認できる。

---

## 4. 設定ファイルをバックアップ

今回編集するデフォルトサイト設定は以下。

```text
/etc/nginx/sites-available/default
```

変更前にバックアップを作成した。

```bash
sudo cp /etc/nginx/sites-available/default /etc/nginx/sites-available/default.bak
```

---

## 5. 意図的に設定ミスを作成

設定ファイルを編集した。

```bash
sudo nano /etc/nginx/sites-available/default
```

`listen 80 default_server;`の末尾にあるセミコロンを削除し、意図的に文法エラーを作成した。

変更後、Nginxを再起動せずに次を実行した。

```bash
sudo nginx -t
```

結果として、23行目付近に設定エラーがあることが表示された。

実際に変更した位置も20行目以降だったため、エラー位置の検出がおおむね正しいことを確認できた。

なお、設定ファイルのエラー位置として表示される行は、必ずしも間違えた文字そのものの行とは限らない。

例えば前の行でセミコロンを付け忘れた場合、Nginxが次の設定項目を読み込んだ時点で文法がおかしいと判断し、次の行をエラー位置として表示する場合がある。

---

## 6. バックアップから復旧

作成しておいたバックアップを元の設定ファイルへ戻した。

```bash
sudo cp /etc/nginx/sites-available/default.bak /etc/nginx/sites-available/default
```

その後、

```bash
sudo nginx -t
```

を再実行し、設定が正常に戻ったことを確認した。

さらに、

```bash
sudo systemctl status nginx --no-pager
```

でNginxが引き続き稼働中であることも確認した。

## 今日理解したこと

### Netplanの`optional: true`

ネットワークインターフェースが使用可能になるまでOS起動を待たせないための設定。

検証環境のようにNICを意図的に切断したり、複数VMを同時起動したりする場合に便利だった。

### `nginx -t`

Nginxの設定ファイルを実際に反映する前に、文法エラーを確認できる。

設定変更時は、

1. 設定ファイルをバックアップ
2. 設定を編集
3. `nginx -t`で確認
4. 問題がなければreloadまたはrestart

という流れにすると安全性が高い。

### 設定ファイルを書き換えただけでは稼働中サービスは変わらない

今回、設定ファイルを意図的に壊した状態でもNginx自体は正常に動作していた。

これは、設定ファイルを変更しても、Nginxがその設定を再読み込みするまでは現在の設定で動き続けるためである。

## 次回候補

次回は以下のいずれかを検証する。

* `systemctl reload nginx`と`restart`の違い
* 文法としては正しいが、内容が間違っているNginx設定の障害再現
* `/var/log/nginx/error.log`を使った原因調査
* HTTPステータスコードを使った障害切り分け
