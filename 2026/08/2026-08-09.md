# 2026年8月9日

## 今日やったこと

* Hyper-V上のUbuntu Server検証環境で、Nginxの設定変更やファイル権限、待ち受けポート、UFWの設定を利用して複数のWeb障害を再現し、HTTPの応答やログから原因を切り分ける練習を行った。

---

## 1. Nginxのreloadとrestartを確認

* Nginxの設定反映方法として、`reload`と`restart`の違いを確認した。

```bash
sudo systemctl reload nginx
```

`reload`はNginxを停止せず、設定ファイルを再読み込みする。

```bash
sudo systemctl restart nginx
```

`restart`はNginxを一度停止してから起動し直す。

ログを確認すると、reloadでは再読み込みの記録、restartでは停止と起動の記録が残ることを確認した。

```bash
sudo journalctl -u nginx --since "10 minutes ago" --no-pager
```

---

## 2. 文法は正しいが内容が間違っている設定を再現

Nginxの公開ディレクトリを、存在しない場所へ変更した。

```nginx
root /var/www/not-exist;
```

この設定は文法上は正しいため、

```bash
sudo nginx -t
```

は成功した。

しかし設定をreloadしたあと、

```bash
curl -I http://10.77.0.10
```

を実行すると、

```text
404 Not Found
```

となった。

このことから、

「`nginx -t`が成功する = 設定内容が正しい」

とは限らないことを確認した。

`access.log`では404がすぐ確認できた。

```bash
sudo tail -n 20 /var/log/nginx/access.log
```

一方、`error.log`には今回の404原因を直接示す分かりやすい記録はなく、Nginxのreloadに関するnoticeなどが表示されていた。

---

## 3. ファイル権限不足による403 Forbiddenを再現

Nginxが公開しているHTMLファイルの権限を確認した。

```bash
ls -l /var/www/html/index.nginx-debian.html
```

その後、一時的に次の権限へ変更した。

```bash
sudo chmod 600 /var/www/html/index.nginx-debian.html
```

`600`では所有者のみ読み書き可能となり、Nginxからファイルを読めなくなる。

lab-client01からアクセスすると、

```text
403 Forbidden
```

となった。

`access.log`では403を確認できた。

さらに、

```bash
sudo tail -n 20 /var/log/nginx/error.log
```

では、

```text
open() "/var/www/html/index.nginx-debian.html" failed
(13: Permission denied)
```

という内容を確認できた。

このことから、

* `access.log`：HTTPとして何を返したか
* `error.log`：なぜ処理に失敗したか

という役割の違いを確認できた。

その後、

```bash
sudo chmod 644 /var/www/html/index.nginx-debian.html
```

で権限を戻し、HTTP 200 OKへ復旧した。

## 4. Nginxの待ち受けポートを80から8080へ変更

Nginxの設定を変更し、待ち受けポートをTCP 80からTCP 8080へ変更した。

```nginx
listen 8080 default_server;
```

設定確認後、

```bash
sudo nginx -t
sudo systemctl reload nginx
```

を実行した。

さらに、

```bash
sudo ss -lntp
```

でTCP 8080がLISTEN状態になっていることを確認した。

### TCP 80へアクセス

```bash
curl --connect-timeout 5 -I http://10.77.0.10
```

TCP 80ではNginxが待ち受けていないため、即座に接続失敗した。

### TCP 8080へアクセス

```bash
curl --connect-timeout 5 -I http://10.77.0.10:8080
```

Nginxは8080番で待ち受けていたが、UFWで8080番を許可していなかったためタイムアウトした。

そこで、

```bash
sudo ufw allow in on eth1 to any port 8080 proto tcp
```

を追加すると、8080番でHTTP 200 OKが返るようになった。

---

## 5. 不要なUFWルールを削除

検証終了後、Nginxの待ち受けポートを80番へ戻した。

その後、

```bash
sudo ufw status numbered
```

でUFWのルールを確認し、検証用に追加した8080番の許可ルールを削除した。

今回、

「サービス側の設定を元に戻しても、ファイアウォールの許可ルールは自動では消えない」

ことを確認した。

設定変更後は、

1. サービス設定を戻す
2. 待ち受けポートを確認する
3. 不要なファイアウォールルールを削除する
4. 最後に正常通信を確認する

ところまでを一連の作業として考える必要がある。

---

## 6. 正常設定のまま404を確認

最後に、Nginxの設定を壊さず、存在しないURLへアクセスした。

```bash
curl -I http://10.77.0.10/no-such-page
```

結果は、

```text
404 Not Found
```

となった。

`access.log`にも、存在しないページへのアクセスと404の記録が残っていた。

このことから、404は必ずしもサーバー障害や設定ミスを意味するわけではなく、

「要求されたURLに対応するコンテンツが存在しない」

だけでも発生することを確認した。

## 今回整理できた障害の違い

| 現象            | 主な原因            | 確認方法                 |
| ------------- | --------------- | -------------------- |
| タイムアウト        | UFWによる遮断        | `ufw status`         |
| 即時接続失敗        | 対象ポートに待ち受けなし    | `ss -lntp`           |
| 404 Not Found | コンテンツなし、公開先設定ミス | `access.log`、Nginx設定 |
| 403 Forbidden | ファイル権限不足        | `ls -l`、`error.log`  |
| `nginx -t`失敗  | 設定ファイルの文法ミス     | `nginx -t`           |

## 今日理解したこと

Web障害を調べるときは、単に「つながらない」と考えるのではなく、

1. 通信そのものが届いているか
2. 対象ポートでサービスが待ち受けているか
3. ファイアウォールが許可しているか
4. HTTPステータスコードは何か
5. access.logには何が記録されているか
6. error.logに原因が記録されていないか
7. ファイルや設定内容に問題がないか

という順で原因を絞り込める。

また、設定変更後は「動いたか」だけでなく、検証用のポートやUFWルールなど不要な設定が残っていないか確認することも重要である。
