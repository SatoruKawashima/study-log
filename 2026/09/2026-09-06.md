# 2026-09-06 Linuxサーバー運用・監視ラボ 学習記録（ネットワーク・名前解決）

## 日付

2026-09-06

## やったこと

- `ss -tulpn` / `ss -ltnp` でSSHとNginxの待ち受けポート、待ち受けアドレスを確認
- `ufw status` で22/tcpと80/tcpが許可されていることを確認
- `ip route` で `10.77.0.0/24 dev eth1 ... src 10.77.0.10` を確認し、同一セグメント宛ての経路を確認
- `ip route get 10.77.0.20` で、実際に eth1 と送信元 10.77.0.10 が選ばれることを確認
- `ip neigh show 10.77.0.20` でMACアドレスと neighbor 状態を確認
- ping後に neighbor 状態が `STALE` から `REACHABLE` に変わることを確認
- `ip route get 8.8.8.8` で `Network is unreachable` となり、default routeがなく外部へ出られないことを確認
- `/etc/hosts` に `10.77.0.20 lab-client01` を追加し、手動の名前解決を確認
- `/etc/nsswitch.conf` の `hosts: files dns` を確認し、hostsファイルがDNSより先に参照されることを確認
- `getent hosts lab-client01` で名前解決結果を確認
- `/etc/resolv.conf` の `nameserver 127.0.0.53` を確認し、systemd-resolvedのローカルスタブリゾルバであることを確認
- `resolvectl status` を確認し、現在は実DNSサーバーが設定されていないことを確認

## 理解したこと

- `ss` はサービスがどのポート・アドレスで待ち受けているかを見るために使う
- `0.0.0.0:22` / `0.0.0.0:80` は全IPv4インターフェースで待ち受けている状態
- `ufw` はサービスが待ち受けているかではなく、その通信をファイアウォールで通してよいかを見る
- `ip route` は宛先ごとにどのNIC・経路を使うかを示し、`ip route get` は特定宛先に対する実際の経路選択を確認する
- 同一セグメント内の通信では、ルーティング判断の後にARPで相手IPに対応するMACアドレスを調べ、neighbor tableに保持する
- `STALE` は異常ではなく、保持している近隣情報を最近再確認していない状態。通信後に `REACHABLE` へ変わることがある
- default routeがなければ、同一ネットワーク外の宛先には到達できない
- `/etc/hosts` は手動の名前帳で、小規模環境・検証・一時対応などで使えるが、大規模管理には向かない
- `hosts: files dns` は `/etc/hosts` を先に確認し、見つからなければDNSを使うという意味
- `127.0.0.53` は外部DNSサーバーではなく、systemd-resolvedのローカル受付口
- `resolvectl status` は、名前解決障害時に「実際にどのDNSサーバーを使おうとしているか」を確認するために使う

## つまずき

- `ss` の出力で `0.0.0.0:*` を見てしまい、Local Address側ではなくPeer Address側を見ていた
- `resolvectl status` は表示項目が多く、どこを見ればよいか分かりづらかった
- 名前解決まわりのコマンドは、平常時より「IPなら通るが名前だと通らない」などの障害時に使うイメージがまだ薄い
