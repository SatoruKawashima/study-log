# 2026-09-07 Linuxサーバー運用・監視ラボ 学習記録（名前解決障害の切り分け）

## 日付

2026-09-07

## やったこと

- `/etc/hosts` の `lab-client01` エントリをコメントアウトし、名前解決障害を意図的に再現
- IP直指定では `10.77.0.20` に到達できる一方、`lab-client01` では `Temporary failure in name resolution` になることを確認
- `getent hosts lab-client01` で名前解決結果が返らないことを確認
- `/etc/nsswitch.conf` の `hosts: files dns` を確認し、`/etc/hosts` がDNSより先に参照されることを再確認
- `/etc/hosts` のコメントアウトを原因として特定し、元に戻して復旧
- `getent hosts example.com`、`resolvectl status`、`resolvectl query example.com` を使って、DNSサーバーがない場合の名前解決失敗も確認
- `ping example.com` と `ping 8.8.8.8` を比較し、名前解決障害と経路障害でエラー内容が異なることを確認
- 出力が何もないときの確認方法として `echo $?` と終了ステータスの考え方を学習

## 理解したこと

- IP直指定では通信でき、名前指定だけ失敗する場合は、まず名前解決側を疑う
- `getent hosts` はLinuxの通常の名前解決経路を使って結果を確認できる
- `nsswitch.conf` の `files dns` は、まず `/etc/hosts`、次にDNSを見るという探索順
- `/etc/hosts` に問題がなく、その先のDNS問い合わせが失敗している場合に `resolvectl status` や `resolvectl query` が役立つ
- `Temporary failure in name resolution` は名前からIPへの変換失敗、`Network is unreachable` はIP宛ての経路がないことを示す
- 障害切り分けでは、名前で失敗するのか、IP直指定でも失敗するのかを先に分けると見通しがよい
- Linuxでは「何も表示されない」だけでは成功・失敗を判断できないことがあり、必要に応じて `echo $?` で直前のコマンドの終了ステータスを確認する
- 終了ステータスは基本的に0が成功、0以外は何らかの理由あり。ただし `grep` のように1が「該当なし」を意味するコマンドもある

## つまずき

- コマンドのtypoなのか、本当に検索結果がないのか、出力だけでは迷う場面があった
- 名前解決関連のコマンドは、単体で覚えるより「IPなら通るが名前だと通らない」障害の流れで使う方が理解しやすかった
