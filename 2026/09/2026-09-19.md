# 2026-09-19 Linuxサーバー運用・監視ラボ 学習記録（Nginx障害切り分け・UFW）

## 日付

2026-09-19

## やったこと

- `systemctl --failed` で失敗中のサービスを確認
- `journalctl -p err -b` で今回の起動以降のエラーログを確認
- Nginx の `http {` を一時的に `httpx {` に変更し、設定ミスを意図的に発生
- `nginx -t` で `unknown directive "httpx"` を確認
- `systemctl restart nginx` 後、再起動失敗を確認
- `journalctl -u nginx -b --no-pager` で原因ログまで追跡
- 設定を修正して Nginx を復旧し、`active` を確認
- `ss -lntp | grep :80` と `curl http://10.77.0.10` で待受と実通信を確認
- UFW の 80/tcp 許可を一時的に削除し、Nginx は正常でもクライアントから通信できない状態を再現
- 80/tcp を再許可し、通信復旧を確認

## 理解したこと

- `systemctl --failed` は「現在失敗しているサービス」を見るのに向いている
- `journalctl` には障害が復旧した後も過去の失敗履歴が残る
- `Failed to start nginx.service` は systemd 側の結果であり、具体的な原因は Nginx 自身のログまで追う必要がある
- `-p err` で絞り込みすぎると、`unknown directive` のような具体的な原因ログが見えにくくなる場合がある
- 障害切り分けでは「サービス状態」「待受ポート」「実通信」を分けて確認すると原因層を絞りやすい
- サービスが `active` でも、UFW などネットワーク側で遮断されていれば通信は失敗する

## つまずき

- `journalctl -u nginx -p err -b` では `Failed to start nginx.service` が大量に並び、原因そのものが見つけにくかった
- 重要度で絞り込まず `journalctl -u nginx -b --no-pager` を見ることで `unknown directive "httpx"` までたどり着けた
