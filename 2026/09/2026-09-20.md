# 2026-09-20 Linuxサーバー運用・監視ラボ 学習記録（SSH・名前解決・DNS切り分け）

## 日付

2026-09-20

## やったこと

- UFW で SSH の 22/tcp 許可を一時的に外し、client01 から SSH 接続できない状態を再現
- target01 側で `systemctl status ssh --no-pager` を確認し、SSH サービス自体は `active` であることを確認
- `ss -lntp | grep :22` で 22 番ポートが待受中であることを確認
- `sudo ufw status` で 22/tcp の許可がないことを確認し、UFW が原因と切り分け
- 22/tcp を再許可し、SSH 接続を復旧
- client01 から `ping -c 1 10.77.0.10` で IP 疎通を確認
- `getent hosts lab-target01` で名前解決できない状態を確認
- `/etc/nsswitch.conf` の `hosts: files dns` を確認
- `/etc/hosts` に `10.77.0.10 lab-target01` を追加し、名前解決を復旧
- `getent hosts lab-target01`、`ping -c 1 lab-target01`、`ssh rew@lab-target01` で名前による接続を確認
- `resolvectl status` で DNS が Default Switch 側 NIC に設定されていることを確認
- `getent hosts example.com` で DNS 名前解決を確認
- 外部通信に使う NIC を Hyper-V 側で切断し、DNS が使えない状態を再現
- その状態でも `lab-target01` は `/etc/hosts` で解決でき、`example.com` は解決できないことを確認
- `resolvectl status` で DNS Server 表示が消え、`Current Scopes: none` になることを確認

## 理解したこと

- SSH 接続できなくても、サービスが `active` で 22 番ポートが `LISTEN` しているなら、UFW など通信経路側を疑うべき
- 名前解決は DNS だけではなく、`/etc/hosts` も使われる
- `hosts: files dns` は、まず `/etc/hosts`、次に DNS の順で名前解決することを示す
- `getent hosts` は NSS の設定に従った名前解決結果を確認できる
- 外部 NIC を切断すると DNS サーバーへの経路がなくなり、外部名の解決はできなくなる
- DNS が使えなくても、`/etc/hosts` に登録済みの名前はローカルで解決できる
- `resolvectl status` から、どの NIC が DNS を担当しているか、現在 DNS 問い合わせ可能な状態かを確認できる

## つまずき

- 再構築後だったため、`lab-target01` の名前登録が `/etc/hosts` から消えており、最初から名前解決できない状態だった(ちゃんとバックアップは取ろうね…)
- `getent hosts example.com` では IPv6 アドレスが返ったが、DNS 名前解決自体は正常に動作していることを確認できた

## 次回

- 名前解決障害とルーティング障害の違いを引き続き切り分ける
- 必要に応じて SSH / HTTP / DNS の障害パターンを自力で復習する
