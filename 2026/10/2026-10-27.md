## Data Exfiltration Detection

SplunkとWiresharkを利用し、以下の経路によるデータ持ち出しを検知する演習を行った。

- DNS Tunneling
- FTP
- HTTP
- ICMP

内容そのものは極端に難しくなかったが、実際には「どの条件でフィルタリングすれば異常な通信を見つけられるか」を考える部分に苦戦した。

### DNS Tunneling

DNSクエリの長さや特定ドメインへの問い合わせなどを手掛かりとして、不審な通信を絞り込んだ。

Wiresharkでは、

`dns && frame.len > 70`

などを利用して通常より大きなDNS通信を探したほか、特定ドメインへの問い合わせを確認した。

Splunkでは、送信元IPごとの通信回数、問い合わせドメインごとの件数、異常に長いQueryなどを条件として調査した。

DNSトンネリングでは、通常のDNS通信と比較して不自然に長いQueryや通信頻度が手掛かりになることを確認した。

### FTP

FTPでは認証情報やファイル転送に関係するコマンドを確認した。

Wiresharkで、

- `USER`
- `PASS`
- `STOR`

などのFTPコマンドを絞り込み、必要に応じてTCP Streamを追跡した。

また、特定のファイル名や通常より大きいパケットなどを条件に、ファイル送信の痕跡を探した。

### HTTP

HTTPでは、大量のデータを含むPOSTリクエストを中心に調査した。

SplunkでPOST通信を集計した後、送信量の大きい通信に条件を絞り込み、送信元、宛先、URI、Domainなどを確認した。

その後、Wiresharkでも近いサイズのPOST通信を探し、実際の通信内容を確認した。

単純にPOST通信をすべて見るとノイズが多いため、送信データ量などの条件を追加することが有効だった。

### ICMP

ICMPでは、Echo Requestのサイズを基準として異常な通信を探した。

通常のICMP通信より明らかに大きいパケットを条件にすることで、ICMPを利用したデータ持ち出しの可能性がある通信を絞り込んだ。

### 所感

今回の演習では、SplunkやWiresharkの操作自体よりも、

**「何が異常なのかを考え、それを検索条件へ変換する」**

ことに難しさを感じた。

現時点ではTHMのヒントを参考にフィルターを組み立てることが多かったため、今後は、

**正常な通信の特徴を理解する  
→ 異常の仮説を立てる  
→ SplunkやWiresharkの条件式へ変換する**

という流れを自力で行えるようになりたい。

## Man-in-the-Middle Detection

ネットワークトラフィックから、複数段階のMan-in-the-Middle攻撃を検知する演習を行った。

主に、

- ARP Spoofing
- DNS Spoofing
- SSL Stripping

について調査した。

### ARP Spoofing

ARP Replyや送信元MACアドレスなどを条件にフィルタリングし、ゲートウェイIPに対して不自然なMACアドレスが割り当てられていないか調査した。

また、WiresharkのDuplicate Address Detectionなども利用し、同一IPに対する競合するARP情報を確認した。

ARP Spoofingでは、

**「同じIPアドレスに対して異なるMACアドレスが現れる」**

ことが重要な手掛かりになると確認した。

### DNS Spoofing

まず正規DNSサーバーからのResponseを確認し、その後、それ以外の送信元から返されているDNS Responseを調査した。

その結果、`corp-login.acme-corp.local`に対して不審なDNS応答が存在することを確認した。

さらに調査すると、攻撃者が対象ドメインを自身のIPアドレスへ向ける偽造DNS Responseを送信していることが分かった。

ARP Spoofingによって通信経路へ割り込んだ後、DNS Spoofingによって被害者を攻撃者のサーバーへ誘導する、複数段階のMITM攻撃として整理できた。

### SSL Stripping

対象ドメインが通常はTLSを使用していることを確認したうえで、攻撃者による偽造DNS Responseを追跡した。

被害者が攻撃者のIPアドレスへ誘導された後、本来HTTPSを利用するはずの通信がHTTPとして行われていることを確認した。

このように、本来暗号化されるべき通信が平文HTTPへ切り替わっている場合、SSL Strippingを疑う手掛かりになる。

### Man-in-the-Middle Detectionでの主な学び

今回のシナリオでは、

**ARP Spoofing  
→ DNS Spoofing  
→ 攻撃者のサーバーへ誘導  
→ HTTPによる平文通信**

という攻撃の流れをネットワークトラフィックから追跡した。

MITM攻撃を検知する際には、単一のパケットだけで判断するのではなく、

- IPとMACアドレスの対応関係
- DNS Responseの送信元
- 同一Queryに対する競合したResponse
- 本来HTTPSである通信がHTTPになっていないか

など、複数の兆候を関連付ける必要があると感じた。

## PHP2Shell

PHPランタイムに存在するメモリ安全性の脆弱性について学習した。

攻撃では、メモリ解放後も参照が残る状態や、不完全な内部状態を利用し、情報漏えいによるASLR回避、ヒープ領域の再利用、偽造した内部構造などを組み合わせて、最終的にWebサーバープロセスの権限で任意コマンド実行へつなげる。

攻撃アプローチについては完全には理解できなかったが、対策面では重要な点を理解できた。

PHP2ShellはWordPressやDrupal、Laravelなどのアプリケーション層ではなく、PHPランタイムそのものに存在する。

そのため、Webアプリケーションを更新するだけでは修正できず、修正版PHPランタイムへ更新する必要がある。

また、パッケージ更新後も古いコードを読み込んだWorkerが残る可能性があるため、PHP-FPMやWebサーバーなどの関連プロセスを再起動する必要がある。

### 所感

今回は、ネットワークから攻撃やデータ持ち出しを検知する演習と、PHPランタイムの脆弱性について学習した。

特にネットワーク分析では、WiresharkやSplunkのフィルター構文そのものよりも、

**「攻撃が起きていたら、どのような特徴がログやパケットに残るか」**

を考える能力が重要だと感じた。

現時点ではヒントを見なければ適切なフィルターを思いつかないことも多いため、今後は各プロトコルの正常な挙動と、攻撃時に発生する異常な特徴を結びつけて理解していきたい。
