## Log Analysis with SIEM

SIEMを利用し、複数のログソースから悪性挙動を分析する方法について学習した。

主に、

- Windowsログ
- Linuxログ
- Webログ
- Networkログ

などをSIEMへ取り込み、それぞれを相関させて調査する流れを確認した。

今回はSplunkを利用した。

### SPLについて

Splunkでログ分析を行ったが、SPLについてはまだ自力で組み立てることに難しさを感じた。

現時点では、

**「何を調べたいか考える  
→ 自分でQueryを組み立てる」**

というより、

**「提示されたQueryを利用して結果を確認する」**

という学習になっている部分が大きい。

検索結果を読むことはできても、調査目的をSPLへ変換することが今後の課題だと感じた。

## Alert Triage With Splunk

Splunkを利用してSOC AlertのTriageを行った。

演習では主に、

- Linuxに対するBrute-force
- WindowsのPersistence
- Web Shell
- 複数ログを利用したAlert調査

について確認した。

### Fieldの違い

特に難しかったのは、ログソースによってField名や調査対象が異なる点だった。

例えばIP Addressを探す場合でも、

- `src_ip`
- `clientip`

など異なるField名が利用されていた。

また、Windows、Linux、Web Serverでは記録される情報や見るべきEventも異なる。

そのため、

**「IPを探す」  
「Loginを調べる」**

といった目的だけではQueryを書けず、

1. どのLog Sourceを見るのか
2. どのFieldが存在するのか
3. 何を条件として絞るのか
4. 必要ならどの単位で集計するのか

を整理する必要があると感じた。

覚えたばかりのSPLを組み合わせても、期待した結果にならないことも多かった。

## Alert Triage With Elastic

Elastic Stack / Kibanaを利用し、IIS ServerとWindows Serverに対する不審なActivityを調査した。

主に、

- Web Logの検索
- Windows Logの検索
- IOCの確認
- 複数ログソースの相関
- Alertから侵害の流れを追跡する

といった作業を行った。

### Splunkとの比較

個人的にはElasticの方が操作しやすく、Queryも書きやすいと感じた。

ただし、

- 何を探すべきか
- どのFieldを見るべきか
- 何を表示・集計すべきか

という分析設計の難しさはSplunkと同じだった。

つまり、Toolが変わっても最終的には、

**目的  
→ Log Source  
→ Field  
→ Filtering  
→ Correlation  
→ 判断**

という流れが必要になると感じた。

## Challenge: Disgruntled

Linux Forensicsの知識を利用し、内部不正の可能性があるIncidentを調査した。

会社に恨みを持つ元従業員が、退職前に何らかの悪意ある処理を仕掛けた可能性があるというScenarioだった。

### 最初の調査

権限昇格が行われた可能性があったため、

- `/var/log/auth.log`
- `/var/log/syslog`

などから`sudo`関連の記録を探した。

しかし、該当する情報を見つけることができなかった。

そのため、`journalctl`へ調査対象を切り替え、より広く`root`や権限昇格に関係するEventを確認した。

### 攻撃者の行動の再構成

調査の結果、

- 権限昇格
- `it-admin` Userの作成
- Persistence
- ScriptのDownload
- Scriptの編集・Rename
- `os-update`を装った偽装
- `crontab`への登録

といった痕跡を確認した。

最終的には、一定期間UserがLoginしなかった場合に実行される、Logic Bombのような仕組みが作られていたことを確認した。

### Shell History

`it-admin` UserのShell Historyを確認することで、実行されたCommandを追跡した。

Shell Historyは攻撃者の操作を再構成するうえで有用なArtifactであることを学んだ。

一方で、Shell Historyは削除や未記録の可能性もあるため、単一の証拠だけに依存しないことが重要である。

### Viminfo

Userおよびrootの`viminfo`を調査し、編集されたScript Fileを特定した。

Shell Historyだけでは不足する場合でも、

**Editor Artifactから「何を編集していたか」を確認できる**

ことを学んだ。

今回の演習では、

**Log  
→ Shell History  
→ Editor Artifact**

と複数の情報源を横断して行動を再構成した。

### 反省点

最初は、

**「Privilege Escalationならsudoだろう」**

と考え、`auth.log`や`syslog`を中心に調査した。

しかし結果が得られなかったため、より広いLog Sourceへ切り替える必要があった。

今回の経験から、

**最初の仮説が外れた場合には、別のLog SourceやArtifactへPivotすること**

が重要だと感じた。

## Challenge: ItsyBitsy

Elastic / ELKを利用したIncident Investigation Challengeに取り組んだ。

内容としては比較的簡単で、KQLを自分で複雑に記述する必要はなかった。

### 調査内容

指定された日時の通信Logを確認し、不審な通信を探した。

その結果、

`pastebin.com`

へのAccessを確認し、何らかのFile共有または取得に関係している可能性を突き止めた。

また、`bitsadmin`が利用されている痕跡も確認した。

`bitsadmin`はWindowsの正規Toolだが、File Transferなどに悪用される可能性がある。

今回は具体的に何を取得・実行していたのか、後続挙動の詳細調査までは行わなかった。

## 所感

今日はSplunkとElasticを利用したLog Analysisを中心に、Linux ForensicsやIncident Investigationにも取り組んだ。

特に強く感じたのは、

**Query Languageを覚えるだけでは調査できない**

ということだった。

SplunkでもElasticでも、

- 何を疑っているのか
- どのLog Sourceを見るのか
- どのFieldを使うのか
- どのEventを関連付けるのか

を先に考える必要がある。

また、Disgruntledでは、最初に確認したLog Sourceから情報が得られなかったものの、`journalctl`、Shell History、`viminfo`へ調査対象を切り替えることで攻撃者の行動を再構成できた。

今回の学習を通して、

**「最初の検索で見つからなければ終わり」ではなく、別のArtifactへPivotしながら仮説を修正する**

ことの重要性を実感した。
