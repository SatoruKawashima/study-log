## Shared Responsibility Model

AWSの責任共有モデルについて学習した。

AWS CloudのSecurityでは、

- **Security of the Cloud**　
- **Security in the Cloud**

という責任範囲の違いを理解する必要がある（コレに関してはあらゆるクラウド関係の記述で出ますよね）

AWSはPhysical InfrastructureやCloud基盤などを保護する一方、ユーザー側にも、

- IAM
- Access Key
- Data
- OSやApplication
- Network設定
- Storageの公開設定

など、利用するServiceに応じたSecurity責任が存在する。

また、IaaS / PaaS / FaaS / SaaSによってユーザー側が管理する範囲も変化する。

### 事故事例

責任共有モデルの理解不足や設定不備に関係する事例として、以下を確認した。

#### Capital One

SSRFを起点としてCredentialや権限が悪用された事例を確認した。

Cloud上であってもIAMのLeast Privilegeを徹底する必要があり、必要以上の権限を付与することが重大な被害につながる。

#### Uber

Access KeyなどのCredentialが悪用された事例から、Cloud Credentialの安全な管理の重要性を確認した。

#### Pegasus Airlines

S3 BucketをPublicにしたまま運用したことによる情報漏洩事例を確認した。

### 所感

責任共有モデルはCloudの基本的な内容であり、資格学習でも何度も学習している。

一方、実際のセキュリティ インシデントと関連付けることで、

**AWSが安全なインフラを提供していても、ユーザー側の設定や運用が適切でなければインシデントは発生する**

という意味を改めて理解できた。

## Challenge: Boogeyman 2

Boogeyman 1を飛ばし、推定作業時間が比較的短いBoogeyman 2に挑戦した。

Scenarioとしては、HR担当者が応募者から送られてきたResumeのDOC Fileを開いたことで悪意あるMacroが実行され、Workstationが侵害されたという内容だった。

### Macro Analysis

悪意あるOffice DocumentのMacroを調査した。

Macro Analysisには`olevba`を利用する必要があったが、今回がほぼ初見だったため操作方法が分からず、Walkthroughを参考にしながら調査した。

途中までは`strings`Commandを利用してDocument内の文字列を抽出し、手掛かりを探した。

専用Toolの使い方が分からない場合でも、まずFile内部から情報を抽出して確認する方法があることを経験できた。

一方、Office Macroの調査では`olevba`のような専用Toolを利用した方が効率的であるため、今後使い方を整理しておきたい。

## メモリフォレンジックス

Challengeを進める中で、メモリダンプの調査が必要になることが分かった。

メモリー分析には**Volatility**を利用した。

今回はVolatilityの利用経験がほとんどなかったため、ChallengeそのものよりもToolの使い方に苦戦した。

主に、

- プロセスツリーの確認
- 不審なプロセスの追跡
- メモリダンプ内に残る情報の調査
- `grep`などを利用した悪意あるFile Pathの検索

を行った。

プロセスツリーからマクロ実行後にどのようなプロセスが生成されたのかを確認し、悪意あるファイルがどこへ展開されたのかを調査した。

### Walkthroughの利用

今回は未知のToolが複数登場したため、Walkthroughを参考にしながらChallengeを進めた。

自力だけで完全に調査することはできなかったが、

**Office Macro → プロセス生成 → File展開 → メモリー上のArtifact確認**

というインシデント調査の流れを一度経験することができた。
