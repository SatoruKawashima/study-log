## Basic Malware RE

MalwareTechBlogが作成した、基本的なマルウェアリバースエンジニアリングのChallenge。

実行ファイルを実際には動作させず、静的解析によって指定されたMD5ハッシュの元となる文字列を探した。

解析そのものは難しくなく、疑似マルウェアの変数やメッセージボックスなど、比較的分かりやすい場所に対象となる文字列が含まれていた。

### 環境構築

今回最も苦労したのは解析ではなく環境構築だった。

AttackBoxが利用できなかったため、普段ラボとして利用しているPCのHyper-V上にGUI版Ubuntuを構築し、

- Ubuntuのインストール
- JDKの導入
- Ghidraの導入
- Ghidraによる逆コンパイル

まで実施した。

感覚としては、

**環境構築9割、解析1割**

という内容だった。

解析自体は簡単だったものの、実際に必要な環境を自分で用意してGhidraを動作させるところまで経験できた。

作業量の割にTryHackMe上で得られたスコアが少なかったのは少し残念だった。

## Friday Overtime

Cyber Threat Intelligence Analystとして、架空の脅威インテリジェンスツール「PandaProbe Intelligence」を利用してチケットを処理した。

`pRsm.dll`など複数のDLLサンプルについて調査を行った。

主な流れは、

1. ファイルのハッシュ値を確認
2. VirusTotalなどで照会
3. 必要に応じてAIも利用して追加情報を収集
4. 得られた情報を整理してチケットを処理

というものだった。

技術的にはそれほど難しくなく、これまで学習してきたFile and Hash Threat Intelligenceの流れを実践する内容だった。

マルウェアをすべて自力で解析するのではなく、既存の脅威インテリジェンスを利用して効率的に情報を収集することも重要であると再確認した。

## Volt Typhoon

Splunkを使用して、APTグループによる侵害を調査した。

Cyber Kill Chainに沿ったシナリオが用意されており、複数種類のログから攻撃者の活動を追跡した。

調査では、

- アカウントの乗っ取り
- 内部情報の収集
- Web Shellによる永続化
- Mimikatzの持ち込み
- 認証情報や機密情報の収集
- 情報の持ち出し
- ログ削除などによる痕跡消去

という一連の攻撃活動を確認した。

### 難しかった点

Splunkの操作そのものより、

**「現在分かっている情報から、次に何を調べるべきか」**

が分からなくなる場面があった。

その際はAIに調査観点を確認し、それでも分からない場合にはWriteupを参照した。

ただし、できるだけ直接答えを見るのではなく、調査方針や考え方の説明部分を確認してから自分で続きを調査するようにした。

個々のログを検索するだけではなく、複数の攻撃活動を関連付けて一つの攻撃チェーンとして再構成する総合演習となった。

## The Crown Jewel

SplunkとWiresharkを併用し、重要情報の窃取を目的としたネットワーク侵害を調査した。

`Reverse Shell Outbound Connection Detected`というアラートを起点として、ログとPCAPを分析した。

主に、

- ゲートウェイを偽装したMACアドレスの特定
- ARPスプーフィングの調査
- HTTP POSTリクエストの解析
- 平文で送信された認証情報の確認
- 不自然なサブドメインからDNSトンネリングの兆候を確認

といった調査を行った。

Splunkでイベントを追跡するだけではなく、Wiresharkで実際の通信内容を確認することで攻撃を再構成した。

前日にJr Penetration Testerで平文通信やMITMについて学習した直後だったため、それらが実際の侵害調査へつながる内容でもあった。

Challenge自体は比較的短めだった。

## Cache Me Outside

これまでのChallengeとは方向性が大きく異なり、OSINTを利用して、引退した元ハッカーのオンライン上の痕跡を追跡した。

最初の会話スクリーンショットを起点として、

1. ブログ記事から人物名やGitHubアカウントを特定
2. リポジトリに誤って公開された情報からメールアドレスを取得
3. 同じアカウント名で利用されているSNSを特定
4. SNSに投稿された写真から撮影場所を推定
5. 投稿された日常のルーチンから普段利用している駅を特定

という流れで調査した。

写真の撮影場所については比較的特徴が分かりやすく、ルーマニアのティミショアラにある会社まで絞り込むことができた。

一方、最後の駅の特定は難しかった。

フランス系スーパーマーケットなどの断片的な情報から場所を絞る必要があり、同じ店舗がティミショアラ周辺に複数存在したため、候補の整理に苦戦した。

### 学んだこと

単独では問題にならないように見える情報でも、

**ブログ  
→ GitHub  
→ メールアドレス  
→ SNS  
→ 写真  
→ 生活ルーチン**

と関連付けることで、個人の身元や行動範囲まで絞り込める可能性がある。

SNSへ公開する情報については、直接住所や位置情報を書いていなくても、複数の情報を組み合わせることで個人特定につながる点に注意する必要がある。

## Report Writing for SOC L2

SOC Level 2以降で重要となる、レポート作成について学習した。

L2以上になると技術的な調査能力だけでなく、調査結果を相手が理解し、適切な行動を取れる形で伝える能力も重要になる。

特に印象に残ったのは、レポート作成におけるAI利用についてだった。

AIを利用すれば、

- 文章の整理
- 要約
- 表現の改善
- レポート作成時間の短縮

などが期待できる。

難しい文章を自力で考えることに時間を使いすぎ、肝心の報告が遅れるのであれば、AIを補助として利用することには意味がある。

一方で、AIが生成した文章をレビューして提出した場合でも、

**そのレポートに責任を持つのは提出した人間である。**

特に重要だと感じたのは、

**顧客は、そのレポートがどのように作られたのかには基本的に関心を持っていない**

という点だった。

顧客から見れば、アナリストが提出したレポートはアナリストの成果物である。

AIによるハルシネーションや誤った情報が含まれていたとしても、「AIが書いた可能性があるから間違っていても仕方がない」とは考えてもらえない。

そのため、AIを利用する場合でも、内容を判断・検証できるだけの知識が必要になる。

## Defensive Security Trends

現代の防御側セキュリティにおけるトレンドについて学習した。

特に印象に残ったのは、攻撃の高速化だった。

攻撃側でも自動化やAIの利用が進んでおり、防御側にもより迅速な分析と対応が求められる。

AIはSOC業務の効率化にも利用できる一方、経験の浅いアナリストがAIの分析結果をそのまま信用すると、

- AIによる見落としに気付けない
- 誤検知をそのまま報告する
- 過検知によって顧客へ不要な対応を求める

といった問題につながる可能性がある。

AIが利用される時代になっても、MITRE ATT&CKに整理されている攻撃手法や技術そのものが不要になるわけではない。

むしろ、

**AIの分析結果が妥当なのかを人間が判断するためにも、基礎知識を学び続ける必要がある**

と感じた。
