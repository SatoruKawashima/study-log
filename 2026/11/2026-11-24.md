## Splunk: Exploring SPL

SplunkのSearch Processing Language（SPL）について、基本的な検索より一歩進んだ使い方を学習した。

最近はSplunkを利用するChallengeを多く実施していたため、基本的な検索やフィールド指定、`stats`などについてはある程度既知の内容だと思っていたが、今回はこれまであまり使用していなかった機能が多く登場した。

### `eval`によるデータ加工

ログオン種別の数値を人間が理解しやすい表現へ変換する例として、`eval`と`case()`を利用した。

```spl
index=windowslogs
| eval LogonTypeDesc = case(
    LogonType == 3, "Network Logon",
    LogonType == 5, "Service"
)
| stats count by LogonType LogonTypeDesc
```

ログをそのまま検索するだけでなく、

**生データを加工 → 意味を付与 → 集計**

という処理ができることを確認した。

### `eventstats`によるユーザーごとの異常検知

VPNログでは、ユーザーごとのログイン回数と国別ログイン回数を計算し、普段ほとんど利用されない国からのログインを抽出した。

```spl
index=vpnlogs
| eventstats count as logins_by_user by user
| eventstats count as logins_by_user_country by user src_country
| eval country_freq=logins_by_user_country/logins_by_user
| where country_freq < 0.1
```

`stats`とは異なり、`eventstats`では集計値を元のイベントに付与できる。

これにより、

**「海外からのログインだから怪しい」ではなく、そのユーザー自身の通常行動と比較して珍しいか**

という視点で調査できる。

### 統計を利用したログイン時刻の異常検知

さらに、ユーザーごとの平均ログイン時刻と標準偏差を求め、z-scoreを利用して普段と大きく異なる時間帯のログインを抽出した。

```spl
index=vpnlogs
| eval hour=tonumber(strftime(_time, "%H")) + tonumber(strftime(_time, "%M"))/60
| eventstats avg(hour) as typical_hour stdev(hour) as stdev_hour by user
| eval zscore=abs(hour - typical_hour) / stdev_hour
| where zscore > 3
```

これまでChallengeで利用してきたSPLは、

**「怪しいログを条件で検索する」**

という用途が中心だった。

今回は、

**ログそのものから通常状態を計算し、その基準から外れたものを異常として抽出する**

という使い方まで踏み込んだ。

Splunkは単なるログ検索だけでなく、ログの加工、統計処理、異常検知まで実行できることを改めて確認した。

## OpenSSH: CVE-2026-123158

脇道として、OpenSSHとmusl libcの組み合わせで発生したCVE-2026-123158について学習した。

軽量LinuxディストリビューションであるAlpine Linuxなど、PAMを利用せずOpenSSHから直接`crypt()`を利用する構成で問題となる脆弱性だった。

### 脆弱性の原因

Linuxでは`/etc/shadow`にパスワード情報が保存され、ロックされたアカウントでは`*`が利用される場合がある。

一方、musl libcの`crypt()`は処理に失敗した際、`NULL`ではなく文字列`"*"`を返す実装となっていた。

さらに、muslのSHA-256-crypt / SHA-512-cryptでは非常に長いパスワードを渡した場合に処理が失敗し、`"*"`が返される。

そのため、

**ロック済みアカウント側の値：`*`  
`crypt()`失敗時の戻り値：`*`**

という衝突が発生し、認証処理で一致したものとして扱われる可能性が生じていた。

個々の仕様だけを見ると問題が表面化しなかったものが、複数の実装を組み合わせたことで認証バイパスにつながった点が興味深かった。

### ラボでの確認

意図的に脆弱なAlpine Linux環境に対して、非常に長い同一文字のパスワードを使用してSSH認証を試した。

`AAAAAAAAAAAAAAAAAAA...(全部で257バイト分くらいのAの羅列)`

最初の試行では失敗したが、再度同じパスワードを入力すると認証を突破できた。

特別なExploit Toolではなく、通常のSSHクライアントと長いパスワードだけで認証を突破できることを実際に確認した。

### 緩和策

根本的には、この問題が修正されたバージョンへ直ちにアップデートすることが最善となる。

アップデートをすぐに適用できない場合は、

- 公開鍵認証を設定
- パスワード認証を無効化

することで影響を緩和できる。

また、PAMを使用している構成など、同じOpenSSHでも環境によって影響条件が異なることも重要だった。

## 所感

今日はSplunkの応用的なSPLと、比較的新しいOpenSSH関連の脆弱性について学習した。

SPLについては、Challengeを繰り返していたため基本的な使い方には慣れてきたと思っていたが、

- `eventstats`
- `eval`
- 標準偏差
- z-score

などを利用し、ログから通常状態を作って異常を検出する方法はほとんど触れたことがなかった。

単に条件に一致するログを探すだけではなく、

**「何を異常とするか」をデータから作る**

という使い方ができることが印象に残った。

CVE-2026-123158では、OpenSSH単体の問題ではなく、

**OpenSSH  
＋ musl libc  
＋ PAMを利用しない認証構成  
＋ `/etc/shadow`のロック表現**

という複数要素の組み合わせによって問題が生じていた。

脆弱性は必ずしも一つの製品内部だけで完結するものではなく、それぞれのコンポーネントが持つ仕様の境界部分で発生することもあると改めて感じた。
