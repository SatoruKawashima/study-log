## n8n: CVE-2026-119408

n8nの非推奨ノードとvm2 sandboxを利用した脆弱性について学習した。

n8n自体をこれまで利用したことがなく、Workflow、Node、Task Runner、vm2、環境変数など複数の前提知識が一度に登場したため、Roomの解説を読みながらハンズオンを進めても内容を十分に整理できなかった。

クリアまでには約2時間かかった（第三者によるライトアップもウォークスルーもなかったのでチートが使えず、自力が試されました…ただの解説を読んでハンズオンするだけなのに…）

ハンズオン自体は手順に沿って最後まで実施したものの、終了時点でも脆弱性の全体像を理解したとは言いづらかったため、学習後にAIへ内容を要約してもらい、ようやく構造を整理することができた。
※先に断っておくと、ここから先はほぼAIからの受け売りです。がんばってハンズオンを終わらせるところまでが私の限界でした。

## n8nと今回の問題

n8nは、複数の処理をNodeとして接続し、Workflowとして自動化できるツールである。

以前はJavaScriptを実行するために、

- Function node
- Function Item node
- LangChain Code node

などが利用されていた。

これらは後に新しいCode nodeへ置き換えられ、画面上のNode Paletteからは非表示となった。

しかし、非表示になっただけでNode自体はバックエンドへ残っており、Workflow JSONにNode Typeを直接指定すると引き続き読み込み・実行できる状態だった。

今回特に重要だと感じたのは、

**「UIから見えないこと」と「利用できないこと」は別である**

という点だった。

Node Paletteから隠す処理はアクセス制御ではなく、バックエンド側で利用を拒否しなければセキュリティ対策にはならない。

---

## 新旧Nodeの実行場所の違い

現在のCode nodeでは、ユーザーが記述したコードをTask Runnerと呼ばれる隔離された実行環境で処理する。

一方、今回問題となった古いNodeは、n8n本体と同じプロセス内でvm2 sandboxを使用してコードを実行していた。

つまり、

**新しいCode node  
→ n8n本体とは分離されたTask Runner**

**旧Node  
→ n8n本体プロセス内のvm2**

という違いがあった。

古いNodeでは、ユーザーコードとn8n本体との距離が近く、sandboxから本体側の情報へアクセスできた場合の影響が大きくなる。

---

## 環境変数の読み取り

LangChain Code nodeでは、`@langchain/core`の一部モジュールを読み込むことが許可されていた。

その中にある`getEnvironmentVariable()`を利用すると、sandbox内から呼び出しているにもかかわらず、n8n本体プロセス側の環境変数を参照できた。

Roomでは最初に影響の小さい環境変数を読み出して経路を確認した後、

- `N8N_ENCRYPTION_KEY`
- 検証用のCanary値

を取得した。

今回ようやく理解できたポイントは、

**vm2そのものを直接突破したというより、sandboxから利用を許可されたモジュールの関数が、sandbox外の実行環境を参照していた**

という点だった。

---

## 暗号鍵が持つ意味

`N8N_ENCRYPTION_KEY`は、n8nが保存する認証情報や各種Secretを暗号化するために利用される。

暗号鍵だけを取得しても直ちにすべての情報が復号できるわけではないが、

**暗号化されたデータストア + Encryption Key**

が揃えば、保存された認証情報などを復号できる可能性がある。

そのため、環境変数の読み取りが単なる情報漏洩ではなく、より大きな影響につながり得ることを確認した。

---

## 修正版の動作

脆弱なProduction環境では、非推奨Nodeを含むWorkflow JSONを一般のMember権限でImport・Save・Executeできた。

一方、修正版が導入されたStaging環境では、同じWorkflowを保存しようとするとバックエンド側で拒否された。

つまり修正では、

**非推奨Nodeを含むWorkflowを新たに追加・変更することをSave時に拒否する**

仕組みが追加されていた。

---

## Save / Run Asymmetry

ただし、アップデートを適用すればすべて解決するわけではない。

修正版では非推奨Nodeを新たに保存することはできないが、

**パッチ適用前から保存されていたWorkflowは、そのまま実行できる**

という問題が残る。

RoomではこれをSave / Run Asymmetryとして説明していた。

そのため、アップデート後には保存済みWorkflowを調査し、

- `n8n-nodes-base.function`
- `n8n-nodes-base.functionItem`
- `@n8n/n8n-nodes-langchain.code`

が残っていないか確認する必要がある。

パッチの適用だけではなく、既存資産の棚卸しも必要になる。

---

## 対策

根本的な対策は修正版へのアップデートとなる。

すぐにアップデートできない場合には、

- `NODES_EXCLUDE`で問題のNodeを読み込ませない
- Workflowの作成・編集権限を信頼できる利用者のみに制限する

といった緩和策がある。

ただし、これらは完全な修正ではなく、一時的な対策として扱う必要がある。

## 所感

今回はRoomの解説を読み、ハンズオンも最後まで実施したが、終了時点では内容を十分に理解できなかった。

特に、

- n8n独自のWorkflow / Node構造
- Task Runner
- vm2
- Node.jsのModule
- Closure
- 環境変数
- Workflow JSON
- Save時とRun時の挙動差

など、初めて触れる概念が一度に登場したことで、どこが脆弱性の本質なのか見失いやすかった。

そのため、学習後にAIへ内容を要約してもらい、

**非推奨NodeがUIから隠されただけでバックエンドでは利用可能だった  
→ 旧Nodeはn8n本体プロセス内で実行されていた  
→ 許可されたModule経由で本体の環境変数を読めた  
→ 修正版では保存を拒否するようになった  
→ ただし既存Workflowは残るため棚卸しが必要**

という流れに整理して、ようやく理解できた。

今回は「ハンズオンを完走した＝理解できた」とはならなかった。

知らない製品の内部構造を前提にした脆弱性では、手順を再現するだけでなく、その製品が本来どのように動作するのかを整理してから脆弱性を見る必要があると感じた。
